# Item #9990969 — CIRC-09 Fase 2: endpoint de jerarquía Módulo→Épica→Item→Sub-item con lazy-load

## 2026-09-11 20:35 — Implementado, verificado y mergeado

Sub-item de #9990934 (CIRC-09: Panorama en árbol). Ejecuta la FASE 2 del prompt original del
padre: construir el o los endpoints que arman la jerarquía Módulo → Épica → Item → Sub-item con
contadores por nivel, calculados en SQL.

**Decisiones ya resueltas por Irving en el brief del propio item** (verificadas contra hash
`substr(sha1(texto_opción), 0, 16)` de cada `opcion_elegida`, las 3 coinciden con la opción
recomendada):
- q1 → un solo endpoint parametrizado `GET .../torre/panorama-jerarquia?nivel=X&parent_id=Y`
  que devuelve solo los hijos directos del nodo pedido (nunca el árbol completo).
- q2 → payload mínimo por nodo: `id`, `titulo`, `nivel`, `tiene_hijos`, `contador_hijos`, `estado`.
- q3 → reusar el permiso `roadmap_view` existente (no crear permiso Spatie nuevo).

**Implementación:**
- `RoadmapController::panoramaJerarquia()` (nuevo) + 3 helpers privados (`sqlVivo`, `sqlActivos`,
  `sqlDetenidos`) que arman las condiciones SQL como strings reusables por alias de tabla.
- `nivel=modulo` (sin `parent_id`): agrega directo sobre `roadmap_items` agrupando por la columna
  `modulo` (no es tabla propia), contando solo hijos raíz (`origen_item_id IS NULL`).
- `nivel=epica` (`parent_id`=nombre de módulo) y `nivel=item` (`parent_id`=id de cualquier item,
  RECURSIVO — sirve igual para hijos de una épica que para nietos de cualquier item, caso real
  MR-23 con sub-épicas encadenadas vía `origen_item_id`): self-join
  `roadmap_items AS parent LEFT JOIN roadmap_items AS child ON child.origen_item_id = parent.id`,
  contadores `SUM(CASE WHEN ... THEN 1 ELSE 0 END)` en 3 baldes:
  - `activos` = una terminal lo trabaja ahora (`en_progreso` / `in_progress` / `en_desarrollo_humano`)
  - `detenidos` = frenado (`requiere_irving` / `bloqueado_por_bucle` / colisión en vuelo /
    `excluir_pool_automatico`)
  - `en_cola` = vivo y no cae en los dos anteriores
- Por default solo cuenta lo VIVO (`archivado_at` NULL, `status`/`estado_aprobacion` no cerrados) —
  los completados no viajan salvo que se despliegue ese nodo, tal como pedía el criterio del padre.
- Paginación (`page`/`per_page`, tope 200) dentro de `nivel=epica`/`nivel=item` cuando un módulo
  trae más de 200 hijos.
- Ruta nueva: `GET /api/roadmap/torre/panorama-jerarquia` (bajo el grupo `web`+`auth` existente),
  gate `roadmap_view` vía `$this->authorize()` dentro del controller (mismo patrón que el resto
  de endpoints de la Torre — `torreSemaforo`, `torreCola`, `atorados`, etc.).

**No hecho a propósito (documentado para la Fase 4, instrucción explícita del padre):** la "fase
actual" del pipeline (Triage/Decisión/Rama/Editando/Verificando/Integrando) NO existe como columna
— no se inventó aquí. Se deja anotado en el docblock del método que puede derivarse de
`estado_aprobacion` + presencia de `branch`/`merge_commit`, ya resuelto como accessor PHP en
`RoadmapItem::getEstacionAttribute()`/`getEstadoColaAttribute()`, pero no como columna ni
expresión SQL agregable — eso lo resuelve quien construya la Fase 4 (UI).

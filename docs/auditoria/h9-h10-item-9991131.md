**Hallazgo confirmado (H9 real):** `finance_edit_payments` es asignable desde el editor de roles
(`resources/js/components/module/adminstration/rol/helper/constants.js:928`, con `depend:
finance_view_payments`) y aparenta gatear la edición de pagos desde `/finanzas/pagos`. Pero
**ningún route ni controller lo checa** — la edición/borrado real de un pago
(`cliente/billing/payment/update/{id}`, `.../destroy/{id}`) está gateada por un permiso
**distinto**: `client_payroll_payment_edit_client` (`config/route_permission.php:198-202`), que
vive bajo el árbol de permisos de la ficha del cliente, no bajo Finanzas. Un rol con
`finance_edit_payments` (y sin `client_payroll_payment_edit_client`) **cree que puede editar
pagos y no puede**; y viceversa. Mismo patrón en `finance_delete_payments` (declarado en la UI,
0 enforcement).

**Familia `panel_view_*` (ids 41-44 — prospects/sales/stadistics/billing):** las 4 tienen **cero**
referencias en todo el código (ni rutas, ni Blade, ni `rol/helper/constants.js`, ni
`migrations_old/`) — no es deriva de nombre (no hay un nombre alterno que sí se cheque), es un
**permiso completamente huérfano**: existe en la tabla `permissions` (ids 41-44) y se le puede
asignar a un rol, pero no gatea absolutamente nada y no aparece ni en el editor de roles hardcoded
(solo sería visible, si acaso, por el catálogo dinámico `/administracion/permisos/catalog`).

## H10 — Doble capa legacy de permisos

**Método:** grep de `can_view|permiso_modulo|acl_|permission_id` en `app/Models/` y
`database/migrations/`, más barrido completo de `information_schema.COLUMNS` de toda la BD
buscando columnas `can_%`/`%acl%`/`%permiso%`/`permission` fuera de las tablas propias de Spatie.

**Candidatas encontradas (y descartadas como "doble capa" real):**

| Tabla.columna | Qué es | ¿Es una capa paralela con enforcement propio? |
|---|---|---|
| `permission_scopes.criterio_propios` + `role_permission_scopes` | Metadata declarativa de "alcance propio" (item #851), FK a `permissions.id` | **No** — extensión aditiva sobre Spatie, el propio migration comment dice "no filtra nada todavía"; no es una tabla de permisos paralela. |
| `module_sidebar_config.permission` | String con el nombre de un permiso Spatie, usado SOLO para decidir si el link del sidebar se muestra | **No** — es una referencia de texto a un permiso Spatie real, consumida vía `auth()->user()->can($childPermission)` (`gestion-red.blade.php:60`). Sigue siendo Spatie, no un sistema alterno. |
| `ipv6_policies.acl_profile` | Perfil de ACL de red IPv6 (MikroTik) | **No** — ACL de red, nada que ver con permisos de usuario del sistema. |
| `torre_permiso_decisiones.permiso` | Registro de decisiones de "compuertas" del propio Circuito CC/Jarvis | **No** — es el sistema de gates del circuito de automatización, no el sistema de permisos de usuarios. |
| `users`, `modules` | — | **Sin columnas** `can_*`/`acl_*`/`permiso_*` en ninguna de las dos (verificado con `Schema::getColumnListing`). |

**Veredicto H10: DESCARTADA.** No existe una tabla o campo legacy que actúe como ACL paralelo
donde la UI escriba y el enforcement real nunca lea (o viceversa). Todo el enforcement real pasa
por Spatie (`model_has_permissions`/`role_has_permissions`) vía `CheckRoutePermission` +
`PermissionTrait`, consistente con lo ya confirmado en items previos de esta misma auditoría
(Fase 3a-bis, #414).

**Hallazgo colateral (no es H10, pero es del mismo vecindario — YA RASTREADO):** la fila
`gestion-red-mikrotik-sync` de `module_sidebar_config` tiene `permission=NULL` → el link del
sidebar se muestra a **cualquier** usuario autenticado (`@if(!$childPermission || ...)` en
`gestion-red.blade.php:59`), aunque la ruta real (`/red/mikrotik-sync`) SÍ está protegida por
`mikrotik_sync_view_dashboard` en `config/route_permission.php` (la ruta rechaza igual; es un
problema de visibilidad de UI, no de acceso real). Ya es el hallazgo documentado en el item #848
→ sub-item **#856** ("los `dynamic_children` de `module_sidebar_config` no tienen chequeo de
permiso individual") — no se abre item nuevo, ya existe.

## Resumen para el sub-item de consolidación (hermano de este item)

- **H9: CONFIRMADA.** Al menos 1 caso claro de deriva de nombre con impacto real
  (`finance_edit_payments`/`finance_delete_payments` vs `client_payroll_payment_edit_client`) +
  1 familia de 4 permisos completamente huérfanos (`panel_view_prospects/sales/stadistics/billing`,
  ids 41-44).
- **H10: DESCARTADA.** No hay capa legacy paralela de permisos; las candidatas encontradas son
  extensiones declarativas sobre Spatie o sistemas no relacionados (red, circuito interno).
- Por decisión de Irving (q3 de este item, opción 1): estos hallazgos se abren como **items
  nuevos** de remediación (no se toca código de permisos en este item) — pendiente de que la
  Fase 3a y este item cierren para que el sub-item de consolidación final los levante.
